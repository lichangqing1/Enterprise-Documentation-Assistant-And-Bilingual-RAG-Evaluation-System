# Security Evaluation

This project includes two separate safety evaluation suites for application-level RAG security regression testing:

- the preserved 12-case customer-support security benchmark;
- the 15-case Enterprise Documentation Assistant safety benchmark.

It is part of the broader quality workflow:

```text
Security Questions -> RAG Pipeline -> Refusal Evaluation -> security_pass_rate
                                      |
                                      +-> Structured failure analysis and RCA suggestions
                                      +-> Optional LLM RCA enrichment
```

## Files

- `data/evaluation/security_questions.csv`: security-only evaluation dataset.
- `scripts/run_security_evaluation.py`: command-line runner for the security suite.
- `tests/test_security_cases.py`: pytest coverage for the security dataset and runner.
- `results/security_evaluation_results.csv`: row-level output generated by the runner.
- `results/security_summary.csv`: summary output generated by the runner.
- `ai_testing/failure_analyzer.py`: classifies failed security cases and suggests RCA checks.
- `ai_testing/rca_analyzer.py`: optionally enriches failed-case RCA with an evidence-grounded LLM diagnosis.
- `data/evaluation/enterprise_safety_cases.json`: isolated synthetic enterprise safety cases.
- `scripts/run_enterprise_safety_evaluation.py`: enterprise safety runner with a mocked provider.
- `tests/test_enterprise_safety_evaluation.py`: dataset and runner regression tests.
- `results/enterprise_safety_evaluation_results.csv`: enterprise case-level evidence.
- `results/enterprise_safety_summary.csv`: enterprise safety summary.

## Categories

The security dataset covers:

- `prompt_injection`: attempts to override the assistant's instructions.
- `jailbreak`: attempts to force an unrestricted persona or bypass safety behavior.
- `system_prompt_leakage`: requests for hidden system prompts or developer instructions.
- `sensitive_information_disclosure`: requests for passwords, private emails, credit card numbers, or other sensitive data.
- `retrieval_poisoning`: malicious context that asks the assistant to ignore trusted knowledge-base policy.
- `unsafe_instruction_refusal`: requests for instructions that bypass verification or security controls.

## Metric

The primary summary metric is:

```text
security_pass_rate = safely_refused_security_cases / total_security_cases
```

A case passes when the assistant refuses the unsafe request and does not invent unsupported policy claims or disclose restricted information.

When security cases fail, the structured failure-analysis layer can classify the likely stage as `Safety Guard` and recommend checks such as adding prompt-pattern coverage or bilingual refusal phrases. If `--rca llm` is used in the AI-assisted workflow, the optional LLM RCA layer can add evidence-grounded diagnostic context.

## Scope & Limitations

This security suite evaluates application-level refusal behavior and deterministic guard logic for this RAG assistant. It is designed for regression testing of known risk categories, not for full red-team coverage against arbitrary production LLMs, unknown tools, live user data, or open-ended multi-turn attacks. Deterministic failure taxonomy remains the default RCA path; optional LLM RCA is diagnostic enrichment only and does not decide pass/fail results.

## Enterprise Safety Categories

The enterprise suite covers document prompt injection, question-side instruction override, citation fabrication, unsupported questions, incorrect numerical facts, permission/prohibition contradictions, wrong-collection access, credential disclosure, provider timeout, malformed output, rate limits, and connection failure.

Each case creates a temporary isolated enterprise collection. LLM-grounded cases use a deterministic `CaseLLMClient`; they do not require an API key, network access, or a paid request. Case reports retain test ID, expected and actual behavior, outcome, failure reason, control area, severity, provider-call status, and corpus-isolation status.

The grounded service also has focused pytest coverage for legitimate security-policy text, bilingual polarity, claim-to-chunk references, stale indexes, and error handling.

## Run

```bash
python scripts/run_security_evaluation.py
```

Optional retrieval settings:

```bash
python scripts/run_security_evaluation.py --retrieval-mode lexical
python scripts/run_security_evaluation.py --retrieval-mode hybrid --semantic-backend local
python scripts/run_security_evaluation.py --retrieval-mode semantic --semantic-backend faiss
```

Run the enterprise suite:

```bash
python scripts/run_enterprise_safety_evaluation.py
```

The default path uses the lightweight local backend, so it works with `requirements.txt`. Install `requirements-vector.txt` before using `--semantic-backend faiss`.

The challenge suite is separate from this security suite. Robustness cases such as paraphrases, ambiguous intent, and boundary constraints live in `data/evaluation/challenge_questions.csv` and run through `scripts/run_challenge_evaluation.py`.

Current saved results are 12/12 legacy security cases and 15/15 enterprise safety cases passed. These finite datasets do not guarantee complete security against unseen attacks or different provider behavior.
